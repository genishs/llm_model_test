02. 브라우저 드래곤플라이트 대회

1. 한 줄 요약

같은 지시문으로 로컬 LLM 15종이 각자 브라우저용 세로 스크롤 슈팅 게임 「dragonflight」를 만들고, 자동 실행 시험과 블라인드 코드 리뷰로 1000점 만점 채점하는 대회입니다. 01 테트리스 대회와 같은 틀이고, 같은 15종이 같은 조건으로 참가합니다.

  • 참가 모델 15종의 제원은 00_model_info 에 있습니다.
  • 모든 모델은 같은 서버에서, 같은 에이전트 도구로, 같은 지시문을 받고, 한 번에 하나씩 순서대로 일합니다.
  • 테트리스와 다른 점이 하나 있습니다. 지시문에 「필요하면 서브에이전트(subagent)를 만들어 역할을 나눠 진행해도 좋습니다」라는 문장이 들어 있습니다(3절, 5절 참고).

2. 무엇을 만드나, 그리고 라운드 개념 (v1 / v2 / v3)

참고 대상은 넥스트플로어(NEXT FLOOR)가 개발해 2012년 카카오톡 「게임하기」로 서비스한 모바일 종스크롤 슈팅 「드래곤플라이트」입니다. 플레이어(용)가 화면 아래에서 좌우로만 움직이고, 공격은 자동으로 계속 나갑니다. 위에서 가로 한 줄씩 내려오는 적(용)을 격파하거나 피하고, 코인과 아이템을 모으고, 경고가 뜬 줄에 떨어지는 운석을 피하며, 일정 거리마다 나오는 보스를 쓰러뜨리는 종스크롤 슈팅입니다.

이 시험은 원작을 베끼는 시험이 아니라 원작의 「게임성」을 직접 구현하는 시험입니다. 지시문은 원작의 그림·소리·이름 같은 에셋을 복사하지 말고 직접 그린 그래픽(도형, Canvas, CSS, WebAudio 합성 등)으로 만들라고 요구합니다. 원작 에셋을 가져다 쓴 구체적인 증거가 있으면 채점에서 감점합니다(7절).

대회는 테트리스와 마찬가지로 「라운드」로 이어집니다. 같은 모델이 같은 게임을 라운드마다 한 단계씩 발전시킵니다.

라운드과제시작 상태
v1세로 스크롤 슈팅을 처음부터 새로 만들기 — 좌우 이동·자동 발사, 웨이브와 적 체력, 코인과 아이템, 운석 경고, 보스, 점수와 난이도 상승, 시작 화면과 다시 시작, 키보드·마우스 조작, index.html 하나로 실행, README.md 포함빈 폴더
v2만들어 둔 게임에 모바일 터치 조작 추가 — 손가락을 끌어 좌우로 이동, 휴대폰 화면에 맞춤자기 v1 결과물을 복사한 폴더
v3아케이드 게임처럼 스테이지와 크레딧·컨티뉴 도입 — 보스를 쓰러뜨리면 다음 스테이지, 코인을 넣어 크레딧을 쌓아야 시작, 게임 오버 뒤 카운트다운 컨티뉴자기 v2 결과물을 복사한 폴더

v2·v3 의 규칙은 다음과 같습니다.

  • 각 모델은 자기 직전 라운드 결과물만 이어받습니다. 다른 모델의 결과물은 보지 못합니다.
  • 공평성을 위해 이전 라운드 채점에서 나온 결함·피드백은 모델에게 알려 주지 않습니다. 모델은 무엇이 틀렸는지 모른 채 지시문만 받습니다.
  • 모델마다 매번 새 세션을 시작하므로, 모델이 아는 것은 지시문과 폴더 안의 코드뿐입니다(이전 대화 기억 없음).
  • v3 의 「크레딧 코인」은 게임 안에서 줍는 코인과 다른 것입니다. 지시문이 이름·표시·조작에서 구분하라고 요구합니다.

폴더 이름 규칙은 simple_llm_test_{모델약어}_dragonflight_{버전} 입니다.

simple_llm_test_q36_dragonflight_v1    # q36 모델의 v1 결과물
simple_llm_test_q36_dragonflight_v2    # 위 폴더를 복사해서 터치 조작을 추가한 v2 결과물
simple_llm_test_q36_dragonflight_v3    # v2 폴더를 복사해서 스테이지·크레딧·컨티뉴를 추가한 v3 결과물

3. 지시문 원문

모델마다 지시문은 폴더 이름({alias} 자리에 모델 약어)만 다르고 나머지는 글자 하나까지 같습니다. 아래는 실제로 보낸 문장 그대로입니다.

테트리스와의 차이: 세 라운드 모두 마지막 요구사항에 「필요하면 서브에이전트(subagent)를 만들어 역할을 나눠 진행해도 좋습니다.」가 들어 있습니다. 테트리스 지시문에는 이 문장이 없었습니다. 쓰라는 지시가 아니라 써도 된다는 허용이어서, 쓸지 말지와 어떻게 나눌지는 모델이 정합니다.

v1

현재 작업 폴더 이름은 simple_llm_test_{alias}_dragonflight_v1 입니다. 이 폴더 안에 웹 브라우저에서 바로 실행되는 HTML 기반 세로 스크롤 슈팅 게임 dragonflight 를 만들어 주세요. 모바일 게임 「드래곤플라이트」의 게임성을 참고하되, 원작의 그림·소리·이름 같은 에셋은 복사하지 말고 직접 그린 그래픽으로 만들어 주세요.

게임 규칙:
- 플레이어(용)는 화면 아래에서 좌우로만 움직이고, 공격은 자동으로 계속 발사됩니다.
- 적(용)은 가로 한 줄 단위의 웨이브로 위에서 내려옵니다. 적마다 체력이 있어 맞으면 줄어들고 0 이 되면 쓰러집니다. 적에 닿으면 게임 오버입니다.
- 쓰러진 적은 코인을 떨어뜨리고, 가끔 아이템(공격 강화·자석·방어막 등)이 나옵니다.
- 운석이 떨어지기 전에는 해당 줄에 경고 표시가 먼저 나옵니다.
- 일정 거리마다 보스가 나옵니다.
- 날아간 거리와 처치 수로 점수를 매기고, 진행할수록 속도와 적 체력이 올라갑니다.
- 점수·거리·코인을 화면에 표시하고, 시작 화면과 게임 오버·다시 시작을 갖춰 주세요.

요구사항:
- 키보드(←/→)와 마우스로 조작할 수 있게 해 주세요.
- 별도 설치·빌드·서버 없이 index.html 파일을 브라우저로 열면 바로 실행되어야 합니다.
- 필요한 파일은 모두 이 폴더 안에 만들어 주세요.
- 게임 소개, 실행 방법, 조작법, 파일 구성을 정리한 README.md 도 이 폴더에 만들어 주세요.
- 필요하면 서브에이전트(subagent)를 만들어 역할을 나눠 진행해도 좋습니다.

완성되면 만든 파일 목록과 조작 방법을 짧게 정리해 주세요.

- README.md 에 터치 조작 방법을 추가해 주세요.
- 필요하면 서브에이전트(subagent)를 만들어 역할을 나눠 진행해도 좋습니다.
완성되면 바꾼 파일 목록과 터치 조작 방법을 짧게 정리해 주세요.

v3

현재 작업 폴더 이름은 simple_llm_test_{alias}_dragonflight_v3 입니다. 이 폴더에는 앞서 만든 HTML 게임 dragonflight(터치 조작 포함)가 있습니다. 아케이드 게임처럼 스테이지(레벨)와 크레딧/컨티뉴 개념을 도입해 주세요.

요구사항:
- 스테이지: 보스를 쓰러뜨리면 다음 스테이지로 넘어가고, 스테이지가 오를수록 어려워지며, 화면에 현재 스테이지가 표시되어야 합니다.
- 크레딧: 코인을 넣어 크레딧을 쌓고(키보드와 터치 모두 가능), 크레딧이 있어야 게임을 시작할 수 있게 해 주세요. 남은 크레딧을 화면에 표시해 주세요. 이 「크레딧 코인」은 게임 안에서 줍는 코인과 다른 것이니 이름·표시·조작에서 구분해 주세요.
- 컨티뉴: 게임 오버가 되면 카운트다운과 함께 컨티뉴 화면을 보여 주고, 그 사이 크레딧을 써서 이어서 할 수 있게 해 주세요(점수·스테이지 유지). 시간 안에 이어 하지 않으면 타이틀 화면으로 돌아갑니다.
- 게임 흐름: 타이틀(대기) 화면 → 시작 → 플레이 → 게임 오버 → 컨티뉴 → 타이틀 로 끊김 없이 이어지게 해 주세요.
- 기존 기능(키보드·마우스·터치 조작)은 그대로 유지하고, 별도 설치·빌드·서버 없이 index.html 을 브라우저로 열면 바로 실행되어야 합니다.
- README.md 에 스테이지 규칙, 크레딧·컨티뉴 방법, 조작법을 추가해 주세요.
- 필요하면 서브에이전트(subagent)를 만들어 역할을 나눠 진행해도 좋습니다.

완성되면 바꾼 파일 목록과 크레딧·컨티뉴 조작 방법을 짧게 정리해 주세요.

4. 실행 환경

테트리스 대회와 같은 서버, 같은 엔진, 같은 에이전트, 같은 권한입니다. 자세한 값은 01 테트리스 대회의 실행 환경을 보세요.

서버

  • AMD Strix Halo 노트북 서버(Radeon 8060S, 64GB 통합 메모리). 모델 추론은 llama.cpp b11701 (Vulkan), router 모드이고 모델은 한 번에 하나만 올라갑니다.
  • 모델마다 서버에 등록된 자기 프리셋(생각 모드, 샘플링 등)을 그대로 씁니다. 대회용으로 따로 바꾸지 않았고, 각 값은 모델 정보 에 있습니다.

예외: mel (Mellum 2.1)

mel 만 llama.cpp b11539 로 돌립니다. b11701 은 Mellum 의 ffn_moe_down 연산을 F32 로 강제하는데 Vulkan 이 이 연산을 GPU 에서 지원하지 않아 CPU 로 넘어가고, 생성 속도가 4.7배 느려지기 때문입니다. 이 서버의 GPU 에서는 b11539 에서도 NaN 이 없었고 퍼플렉서티도 같아서, mel 차례에만 엔진을 바꾸고 끝나면 b11701 로 되돌립니다. 이유와 수치는 01 테트리스 대회의 같은 항목에 있고, 02 에서도 똑같이 적용합니다.

에이전트

  • opencode v1.18.35 를 opencode run --auto --pure -m halo/{alias} 로 실행합니다(--auto 는 파일 편집·명령 실행을 사람 확인 없이 허용, --pure 는 외부 플러그인 없이 실행).
  • 권한: 파일 편집 허용, 셸 명령 허용, 웹 가져오기(webfetch) 거부. 셸 네트워크는 막지 않았습니다(5절 감사 결과 참고).
  • 모델마다 새 세션, 새 임시 홈 디렉터리에서 시작합니다.
  • 서브에이전트: 모델이 서브에이전트를 만들면 opencode 는 그 서브에이전트를 부모와 같은 모델로 실행합니다. 다른 모델을 부를 수 없고(서버도 한 번에 한 모델만 올라가 있습니다), 서브에이전트는 같은 opencode 안에서 돌기 때문에 같은 샌드박스와 같은 시간 제한 안에 있습니다. 서브에이전트가 보내는 요청도 같은 모델 서버를 지나므로 서버 로그 집계(요청 수, 토큰)에 함께 잡힙니다.

5. 공정성 장치

장치내용
샌드박스(bubblewrap)디스크 전체를 읽기 전용으로 두고, 홈과 데이터 디스크는 빈 영역으로 가려서 다른 모델의 폴더·결과물이 보이지 않습니다. 쓸 수 있는 곳은 자기 프로젝트 폴더와 일회용 임시 홈뿐입니다. 부모 프로세스가 끝나면 함께 종료됩니다.
웹 가져오기 도구 거부웹 가져오기(webfetch) 도구는 거부했습니다. 셸 네트워크는 막지 않았습니다 — 아래 「네트워크 사용 감사」 참고.
시간 제한모델당 라운드당 최대 60분. 넘으면 강제 종료하고 그 시점의 결과물로 채점합니다. 서브에이전트를 쓴 시간도 이 60분 안에 들어갑니다.
냉각 시간모델 사이에 1분 쉽니다. 과열을 막고 직전 모델의 부하가 다음 모델에 영향을 주지 않게 하기 위해서입니다.
같은 지시문폴더 이름 외에는 동일한 지시문. 서브에이전트 허용 문장도 15종 모두에게 똑같이 들어갑니다.
이전 피드백 없음v2·v3 에서도 직전 라운드 채점의 결함·피드백을 모델에게 알려 주지 않습니다.
같은 순서모든 라운드에서 아래 순서를 그대로 유지합니다.
폴더 사전 생성모델이 일을 시작하기 전에 빈 폴더(v1) 또는 직전 라운드 복사본(v2, v3)을 미리 만들어 둡니다. 폴더가 이미 있으면 덮어쓰지 않고 중단합니다.
한 번에 한 라운드라운드가 모두 끝나야 다음 라운드를 시작합니다. 서버에는 한 번에 한 모델만 올라가 있습니다.

네트워크 사용 감사 (2026-10-17 기준, v1 진행 중): 셸 네트워크를 막지 않았으므로 실행 기록을 조사했습니다. 드래곤플라이트 v1 실행 로그 10개(진행 중인 실행 포함)와 도구 호출 전체 기록 10건에서 curl·wget, 외부 URL 요청, 패키지 설치, 외부 fetch, webfetch 시도를 찾았습니다. 결과는 0건 / 결과물 반영 0건입니다. 게임 파일 안의 외부 URL과 내려받은 라이브러리 흔적도 0건입니다. v2·v3 실행 기록은 아직 없어 검사하지 못했습니다. 로그에 남지 않는 호출은 확인할 수 없는 범위입니다.

진행 순서: q36, cn, orn, mg, bolt, lfm, mcv, q38, aw, fn, ff, c7, c7r, c1, mel (mel 은 엔진을 바꿔야 해서 맨 마지막). 테트리스와 같은 순서입니다.

데스크톱 자동 시험 (헤드리스 Chrome, file:// 로 index.html 을 직접 열기, 제한 시간 약 4분)

  1. 페이지 로드, 콘솔 오류·예외 수집.
  2. 시작 시도: 화면 클릭, Enter, Space 입력. 크레딧 코인이 필요한 게임이면 먼저 코인을 넣어 봅니다.
  3. 가만히 두고 화면이 저절로 움직이는지(자동 발사, 적 하강, 배경 스크롤) 확인.
  4. ←/→ 키를 눌러 플레이어가 실제로 움직이는지, 방향이 맞는지 확인.
  5. 약 10초 동안 점수·거리·코인 숫자가 오르는지 확인.
  6. 마우스로 끌어서 움직이는지 확인.
  7. 일시정지 키가 있으면 멈췄다 풀리는지 확인.
  8. 게임 오버까지 가서 다시 시작이 되는지 확인.
  9. 각 단계마다 스크린샷을 저장합니다.

모바일 자동 시험 (v2, v3 · 화면 390x844, 터치 에뮬레이션, 제한 시간 약 3분)

  1. 휴대폰 크기로 로드하고 화면 맞춤(가로 스크롤 없음, 캔버스가 화면에 들어오는지) 확인.
  2. 화면을 탭해서 시작.
  3. 손가락 끌기(touchstart 에서 touchmove, 좌우)로 플레이어가 움직이는지 확인.
  4. 움직이는 동안 점수·거리·코인 숫자가 오르는지 확인.
  5. 게임 오버 뒤 탭으로 다시 시작이 되는지 확인.

아케이드 흐름 자동 시험 (v3 만, 제한 시간 약 7분)

  1. 크레딧 코인 투입(키보드, 터치 버튼)과 남은 크레딧 표시 확인. 게임 안에서 줍는 코인 숫자를 크레딧으로 착각하지 않도록 구분해서 읽습니다.
  2. 크레딧이 없을 때는 시작이 안 되고, 있을 때 시작되는지 확인.
  3. 현재 스테이지가 화면에 표시되는지 확인.
  4. 게임 오버를 일으켜 컨티뉴 카운트다운 화면이 나오는지, 크레딧을 써서 이어 하면 점수와 스테이지가 유지되는지, 시간이 지나면 타이틀로 돌아가는지 확인.

테트리스 시험과 다른 점: 슈팅 게임은 화면이 항상 움직이기 때문에 「화면이 바뀌었나」만으로는 입력에 반응했는지 가릴 수 없습니다. 그래서 플레이어의 위치를 왼쪽 입력 상태와 오른쪽 입력 상태에서 각각 캡처한 화면의 차이로 재서 반응과 방향을 판단하고, 점수·거리·코인은 화면에서 읽은 숫자가 실제로 오르는지로 판단합니다.

채점 방법

  • 블라인드 리뷰: 결과물에 익명 이름(A~O)을 붙여 채점하고, 채점이 끝난 뒤 모델 이름을 공개합니다. 리뷰어는 어느 모델이 만든 것인지 모른 채 채점합니다.
  • 자동 시험은 근거 자료이지 점수가 아닙니다. 화면 픽셀과 숫자를 읽는 휴리스틱이라 틀릴 수 있으므로, 최종 판단은 스크린샷과 코드를 직접 보고 합니다.
  • 모든 감점·가점에는 근거(파일:줄 번호 또는 시험 결과)를 적어야 합니다. 근거 없는 감점은 금지입니다.
  • 아무것도 만들지 못했거나 실행이 안 되면 1-1 은 0점이고, 나머지는 있는 코드만큼만 채점합니다.
  • 추가 과제에서 기존 구조를 망가뜨리거나(복사해 붙인 중복, 입력 코드가 규칙 코드와 뒤엉킴) README 가 새 기능을 반영하지 않으면 2~6 에서 감점합니다.
  • 영역별 담당 리뷰어와 평균 방식은 심사 때 정해지며, 각 결과 절에서 밝힙니다.

실용 순위

1000점 순위와 별도로, 600점 이상인 결과물만 모아 만드는 데 걸린 시간 순으로 나열한 「실용 순위」를 함께 냅니다.

속도는 1000점에 넣지 않았습니다. 같은 서버라도 모델 크기·엔진 설정에 따라 속도가 크게 갈려서, 속도를 점수에 섞으면 품질 비교가 흐려지기 때문입니다. 대신 쓸 만한 품질(600점 이상)을 갖춘 모델 사이에서 얼마나 빨리 끝냈는지를 별도 순위로 보여 줍니다.

8. 진행 기록과 한계

  • 진행: 테트리스 v1~v3 가 끝난 뒤 이어서, 02 는 v1, v2, v3 순서로 한 라운드씩 자동으로 진행합니다. v1 은 2026-10-17 16:36 에 시작했습니다.
  • 표본 수: 모델당 라운드당 1회만 실행합니다. 같은 모델을 다시 돌리면 결과가 달라질 수 있으므로 점수 차이가 작은 구간은 순위보다 경향으로 읽어야 합니다.
  • 서브에이전트 허용: 서브에이전트를 쓰면 요청 수와 생성 토큰이 늘 수 있고, 쓰지 않은 모델과 시간·토큰을 단순 비교하기 어렵습니다. 어느 모델이 서브에이전트를 썼는지는 기록 로그로 확인할 수 있을 때 결과 절에 적습니다.
  • 자동 시험의 한계: 반응 여부는 화면 픽셀의 차이와 읽어 낸 숫자라는 간접 신호입니다. 최종 판단은 코드와 스크린샷을 직접 보고 합니다.
  • 사람이 직접 해 봐야 아는 부분: 헤드리스 시험은 사람이 직접 하는 플레이를 대신하지 못합니다. 실제 조작감, 효과음, 휴대폰 실기 동작은 점수에 반영되지 않은 부분이 있습니다.
  • 원작 비교의 한계: 원작의 세부 규칙을 모두 알고 채점하지는 않습니다. 지시문에 적힌 규칙(7절의 1-2)을 기준으로 삼고, 원작의 분위기는 1-3 에서 코드와 스크린샷으로 봅니다.
