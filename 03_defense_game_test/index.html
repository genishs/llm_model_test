03. 브라우저 디펜스 게임 대회

1. 한 줄 요약

같은 지시문으로 로컬 LLM 15종이 각자 브라우저용 디펜스 게임을 만들고, 자동 실행 시험과 블라인드 심사로 1000점 만점 채점하는 대회입니다. 01 테트리스, 02 드래곤플라이트와 같은 틀(v1 / v2 / v3)이지만, 이번에는 조건을 최소로 줄였습니다.

  • 참가 모델 15종의 제원은 00_model_info 에 있습니다.
  • 모든 모델은 같은 서버에서, 같은 에이전트 도구로, 같은 지시문을 받고, 한 번에 하나씩 순서대로 일합니다.
  • 앞의 두 시험과 다른 점 셋: 게임의 규칙과 장르 해석을 모델에 맡겼고, 주어진 시간이 15분뿐이며, 인터넷 제한이 없습니다(2절의 비교표 참고).

2. 시험 의도와 라운드 개념 (v1 / v2 / v3)

시험 의도

앞의 두 시험은 지시문이 무엇을 만들지 꽤 자세히 정해 주었습니다(테트리스는 아타리판 재현, 드래곤플라이트는 규칙 목록). 이번 시험은 거의 반대입니다. 지시문은 「웹 브라우저에서 실행되는 디펜스 게임」이라는 한 줄뿐이고, 다음을 모두 모델에 맡깁니다.

  • 어떤 디펜스 게임으로 만들지: 장르 해석, 규칙, 세계관, 화면 구성, 조작 방식.
  • 기획과 디자인을 어떻게 진행할지: 혼자 할지, 기획자·디자이너·개발자 같은 페르소나를 정할지, 서브에이전트에게 역할을 나눠 줄지, 기획서나 디자인 문서를 남길지.

그리고 시간을 15분으로 줄였습니다. 앞의 두 시험은 60분 제한이었지만 실제 생성 시간은 대개 3~14분이었고 가장 오래 걸린 것이 약 33분이었습니다. 이번에는 부족한 시간 안에서 기획·디자인·개발을 얼마나, 어떤 순서로 진행하는지가 관찰 대상입니다. 지시문에 실제 시작 시각과 마감 시각을 적어 주고, 마감 순간 폴더에 있는 결과물로 평가합니다.

마지막으로 인터넷 제한을 풀었습니다. 웹 검색, 외부 라이브러리·이미지·소리, 런타임 CDN 사용을 허용하고, 가져온 것은 출처와 라이선스를 README 에 적게 합니다. 페르소나와 서브에이전트도 허용합니다.

라운드

대회는 앞의 두 시험처럼 「라운드」로 이어집니다. 같은 모델이 같은 게임을 라운드마다 한 단계씩 발전시킵니다.

라운드과제시작 상태
v1디펜스 게임을 처음부터 새로 만들기 — 장르·규칙·화면·조작은 모델이 정함, index.html 을 열면 바로 실행, README.md 포함빈 폴더
v2만들어 둔 게임에 모바일 터치 조작 추가, 휴대폰 화면에 맞춤자기 v1 결과물을 복사한 폴더
v3스테이지 4개마다 보스전이 열리도록 구성(예: 4·8·12 스테이지), 보스는 일반 적과 다른 체력과 행동 패턴, 현재 스테이지와 보스전 여부를 화면에 표시자기 v2 결과물을 복사한 폴더

v3 는 보스전 하나만 제한합니다. 02 와 달리 크레딧·컨티뉴는 요구하지 않습니다.

v2·v3 의 규칙은 다음과 같습니다.

  • 각 모델은 자기 직전 라운드 결과물만(v2 는 v1, v3 는 v2) 이어받습니다. 다른 모델의 결과물은 보지 못합니다.
  • 공평성을 위해 이전 라운드 채점에서 나온 결함·피드백은 모델에게 알려 주지 않습니다. 모델은 무엇이 틀렸는지 모른 채 지시문만 받습니다.
  • 모델마다 매번 새 세션을 시작하므로, 모델이 아는 것은 지시문과 폴더 안의 코드뿐입니다(이전 대화 기억 없음).
  • 라운드마다 15분이 새로 주어집니다.

폴더 이름 규칙은 simple_llm_test_{모델약어}_defense_{버전} 입니다.

simple_llm_test_q36_defense_v1    # q36 모델의 v1 결과물
simple_llm_test_q36_defense_v2    # 위 폴더를 복사해서 터치 조작을 추가한 v2 결과물
simple_llm_test_q36_defense_v3    # v2 폴더를 복사해서 보스전을 추가한 v3 결과물

3. 지시문 원문

모델마다 지시문은 폴더 이름({alias} 자리에 모델 약어)과 시간 값만 다르고 나머지는 글자 하나까지 같습니다. 아래는 실제로 보낸 문장 그대로이고, 값이 들어가는 자리만 다음과 같이 적었습니다.

  • 제한 시간은 15 입니다.
  • 「시작」 뒤에는 실행 직전의 실제 시각이 들어갑니다(아래에서는 「(실행 직전 시각)」으로 표기).
  • 「마감」 뒤에는 시작 시각 + 15분이 들어갑니다(아래에서는 「(시작 + 15분)」으로 표기).

세 라운드 모두 인터넷 사용, 외부 라이브러리·이미지·소리 사용, 페르소나와 서브에이전트가 「자유롭게 해도 되는 것」으로 적혀 있습니다. v1 에는 기획서·디자인 문서 같은 산출물을 폴더 안에 남겨도 된다는 문장이 더 들어 있습니다.

v1

현재 작업 폴더 이름은 simple_llm_test_{alias}_defense_v1 입니다. 이 폴더 안에 웹 브라우저에서 실행되는 디펜스 게임을 만들어 주세요.

어떤 디펜스 게임으로 만들지(장르 해석·규칙·세계관·화면 구성·조작 방식)와, 기획과 디자인을 어떻게 진행할지는 모두 맡깁니다.

시간 제한:
- 이 작업에 주어진 시간은 15분입니다. 시작 (실행 직전 시각), 마감 (시작 + 15분) 입니다. 터미널에서 date 명령으로 현재 시각을 확인할 수 있습니다.
- 마감 시각이 되면 작업이 강제로 끝나고, 그 순간 이 폴더에 있는 결과물로 평가합니다.

자유롭게 해도 되는 것:
- 인터넷 검색·자료 조사, 외부 라이브러리·이미지·소리 사용(가져온 것은 출처와 라이선스를 README.md 에 적어 주세요).
- 기획자·디자이너·개발자 같은 페르소나를 정하거나 서브에이전트(subagent)를 만들어 역할을 나눠 진행하기.
- 기획서·디자인 문서 같은 산출물을 남기고 싶다면 이 폴더 안에 두세요.

요구사항:
- index.html 파일을 브라우저로 열면 바로 실행되어야 합니다(별도 설치·빌드·서버 없이).
- 필요한 파일은 모두 이 폴더 안에 만들어 주세요.
- 게임 소개, 실행 방법, 조작법, 파일 구성을 정리한 README.md 도 이 폴더에 만들어 주세요.

완성되면 만든 파일 목록과 조작 방법을 짧게 정리해 주세요.

4. 실행 환경

앞의 두 시험과 같은 서버, 같은 엔진, 같은 에이전트입니다. 자세한 값은 01 테트리스 대회의 실행 환경을 보세요. 이번 시험에서 달라진 부분만 적습니다.

서버

  • AMD Strix Halo 노트북 서버(Radeon 8060S, 64GB 통합 메모리). 모델 추론은 llama.cpp b11701 (Vulkan), router 모드이고 모델은 한 번에 하나만 올라갑니다.
  • 모델마다 서버에 등록된 자기 프리셋(생각 모드, 샘플링 등)을 그대로 씁니다. 각 값은 모델 정보 에 있습니다.
  • mel (Mellum 2.1) 만 llama.cpp b11539 로 돌리는 예외도 같습니다. b11701 에서는 Mellum 의 연산 하나가 GPU 에서 CPU 로 밀려 생성 속도가 4.7배 느려지기 때문입니다. 이유와 수치는 01 테트리스 대회의 같은 항목에 있습니다.

에이전트

  • opencode v1.18.35 를 opencode run --auto --pure -m halo/{alias} 로 실행합니다. 모델마다 새 세션, 새 임시 홈 디렉터리에서 시작합니다.
  • 권한: 파일 편집 허용, 셸 명령 허용, 웹 가져오기(webfetch) 허용. 앞의 두 시험에서는 webfetch 를 거부했습니다.
  • 샌드박스(bubblewrap)의 파일 시스템 격리는 그대로입니다. 다른 모델의 폴더와 서버의 다른 파일은 보이지 않고, 쓸 수 있는 곳은 자기 프로젝트 폴더와 일회용 임시 홈뿐입니다. 달라진 것은 인터넷을 쓸 수 있다는 점입니다.
  • 서브에이전트와 페르소나: 모델이 서브에이전트를 만들면 opencode 는 그 서브에이전트를 부모와 같은 모델로 실행합니다. 같은 샌드박스, 같은 시간 제한 안에서 돌고, 아래의 게이트웨이도 똑같이 지납니다.
  • 시간 제한 15분: 마감이 되면 작업을 강제로 끝내고, 그 순간 폴더에 있는 결과물로 평가합니다.

모델 고정 게이트웨이 (원리)

인터넷을 열면 새로운 위험이 생깁니다. 샌드박스 안의 모델이 대회 서버(모델 서버)에 직접 접속해서 다른 모델을 요청하면, 진행 중인 실행을 방해하거나 다른 모델의 시간을 빼앗을 수 있습니다. 인터넷을 막는 대신 이 길만 막기 위해 다음과 같이 합니다.

  • 샌드박스에는 진짜 API 키를 넣지 않습니다.
  • 대신 실행마다 새로 만든 1회용 토큰을 줍니다. 이 토큰은 대회 서버 앞의 중간 게이트웨이에서만 유효합니다.
  • 게이트웨이는 그 실행에 배정된 모델 하나의 요청만 서버로 전달하고, 다른 모델을 요청하면 거부합니다.
  • 실행이 끝나면(정상 종료, 시간 초과, 강제 종료 모두) 토큰을 폐기합니다.

주소, 경로, 키 같은 구현 세부는 공개 문서에 적지 않습니다.

5. 공정성 장치

장치내용
샌드박스(bubblewrap)디스크 전체를 읽기 전용으로 두고, 홈과 데이터 디스크는 빈 영역으로 가려서 다른 모델의 폴더·결과물이 보이지 않습니다. 쓸 수 있는 곳은 자기 프로젝트 폴더와 일회용 임시 홈뿐입니다. 부모 프로세스가 끝나면 함께 종료됩니다.
모델 고정 게이트웨이진짜 API 키를 샌드박스에 넣지 않고, 실행마다 1회용 토큰으로 그 실행의 모델만 통과시킵니다. 인터넷이 열려 있어도 다른 모델을 불러 진행 중인 실행을 방해할 수 없습니다(4절).
같은 시간모델당 라운드당 15분. 마감 순간 폴더의 결과물로 평가하고, 강제 종료된 결과물도 똑같이 채점합니다. 서브에이전트를 쓴 시간도 이 15분 안에 들어갑니다.
같은 조건인터넷 허용, 외부 에셋 허용, 페르소나·서브에이전트 허용이 15종 모두에게 똑같이 적용됩니다.
냉각 시간모델 사이에 1분 쉽니다. 과열을 막고 직전 모델의 부하가 다음 모델에 영향을 주지 않게 하기 위해서입니다.
같은 지시문폴더 이름과 시작·마감 시각 외에는 동일한 지시문.
이전 피드백 없음v2·v3 에서도 직전 라운드 채점의 결함·피드백을 모델에게 알려 주지 않습니다.
같은 순서모든 라운드에서 아래 순서를 그대로 유지합니다.
폴더 사전 생성모델이 일을 시작하기 전에 빈 폴더(v1) 또는 직전 라운드 복사본(v2, v3)을 미리 만들어 둡니다. 폴더가 이미 있으면 덮어쓰지 않고 중단합니다.
한 번에 한 라운드라운드가 모두 끝나야 다음 라운드를 시작합니다. 서버에는 한 번에 한 모델만 올라가 있습니다.
네트워크 사용 관찰인터넷이 허용이므로 네트워크 사용은 「위반」이 아니라 「관찰」로 집계합니다. 무엇을 내려받았는지, 그것이 결과물에 들어갔는지를 기록해 결과 절에 적습니다. 점수에는 넣지 않고, 가져온 것의 출처 표기만 6절(README·출처)에서 봅니다.

진행 순서: q36, cn, orn, mg, bolt, lfm, mcv, q38, aw, fn, ff, c7, c7r, c1, mel (mel 은 엔진을 바꿔야 해서 맨 마지막). 앞의 두 시험과 같은 순서입니다.

6. 진행 순서 (파이프라인)

모델 한 개당 다음 단계를 거치고, 15종 모두 같은 절차를 반복합니다.

 [폴더 준비]  v1: 빈 폴더 생성 / v2: 자기 v1 폴더를 복사 / v3: 자기 v2 폴더를 복사
      |
      v
 [샌드박스 에이전트 실행]  opencode + 지시문 (15분, 게이트웨이 경유, 인터넷·서브에이전트 허용)
      |
      v
 [서버 로그 집계]  소요 시간, 요청 수, 입력/생성 토큰, 생성 속도,
      |            최대 컨텍스트 길이, 컨텍스트 잘림 여부, 시간 초과 여부
      v
 [네트워크 사용 관찰 기록]  무엇을 내려받았나, 결과물에 들어갔나
      |
      v
 [자동 시험]  헤드리스 Chrome: 데스크톱(모든 라운드), 모바일(v2·v3), 보스전(v3)
      |
      v
 [냉각 1분]  --> 다음 모델
      :
      v
 [블라인드 심사]  결과물에 익명 이름 A~O --> 점수 --> 이름 공개 --> 순위

서버 로그 집계: 에이전트가 끝나면 그 시간 동안의 서버 로그에서 해당 모델 몫만 뽑아 요청 수, 읽은 토큰(프롬프트), 생성한 토큰, 생성 속도(t/s), 최대 컨텍스트 길이, 컨텍스트 초과로 잘린 횟수를 계산하고 결과 폴더의 파일 목록과 크기도 기록합니다. 이번에는 15분 안에 끝났는지, 시간 초과로 강제 종료됐는지도 함께 기록합니다.

자동 시험: 이번 시험은 장르가 열려 있어 모델마다 규칙이 다릅니다. 그래서 시험은 「입력에 화면이 바뀌었나」가 아니라 결과 상태(적 체력 감소·제거, 자원 증감, 기지 체력, 웨이브 번호)를 읽습니다. CDN 사용을 허용했으므로 온라인 상태에서 실행합니다. 시험은 데스크톱(모든 라운드), 모바일 터치(v2·v3), 보스전(v3) 세 가지이고, 시작 경로(키·클릭·탭)를 각각 새 페이지에서 따로 시험합니다. 확인하지 못한 항목은 「없음」이 아니라 「확인 불가」로 기록해, 시험이 보지 못한 것과 게임에 없는 것을 구분합니다. 자동 시험은 사람 심사를 돕는 근거 자료이고 최종 판단은 스크린샷과 코드를 직접 보고 합니다.

이 시험에는 「정답 장르」가 없습니다. 타워 디펜스든 기지 방어든 심사자는 장르를 가정하지 않고, 모델이 스스로 정한 규칙이 일관되게 구현됐는가를 봅니다. 서로 다른 게임을 같은 잣대로 줄 세우기 때문에, 장르 사이의 재미나 완성도 비교는 점수 밖입니다.

판정 원칙 (앞의 두 시험에서 얻은 교훈)

  • 「반응한다」는 「동작한다」가 아닙니다. 결과 상태(적 체력 감소·제거, 자원 증감, 기지 체력, 웨이브 번호)로 확인합니다.

  • 인터넷을 허용했지만 결과물에 외부 라이브러리·에셋·CDN 을 쓴 엔트리는 0개입니다. 게임 파일이 실행 중 불러오는 외부 URL 은 0건이고, 패키지 설치도 이미지·소리 같은 바이너리 에셋도 0건입니다. 15분 안에서는 조사보다 직접 만들기를 골랐다는 뜻입니다. 네트워크 사용은 「위반」이 아니라 「관찰」로 집계한 결과 webfetch 도구 호출은 15종 모두 0회였고, 셸에서 curl·wget 계열 명령을 실행한 것은 q36 의 3회뿐입니다(주소가 남지 않은 호출이고 내려받은 파일은 결과물에 없습니다). 외부 주소가 보이는 곳은 cn 의 README 에 있는 배지 이미지 링크 2개뿐인데, 출처 표기 없이 넣어 6절에서 3점을 깎았습니다. 모델 고정 게이트웨이는 다른 모델을 요청하는 시도를 한 건도 막은 적이 없습니다(거부 0건).

  • 장르 해석은 경로형 타워 디펜스가 다수였습니다. 12종 중 8종(fn·q38·mg·ff·cn·q36·orn·mcv)이 경로형 타워 디펜스이고, 4종은 슈팅·사격형입니다. 이 가운데 aw(기지 이동·자동 사격)와 mel(방향키 이동·클릭 발사), lfm(세로 슈팅)은 하단의 아군을 움직여 적을 쏘는 방어이고, bolt 는 고정 기지에서 마우스 방향으로 직접 조준해 쏩니다. 자원 경제와 배치를 가진 것은 경로형 타워 디펜스뿐입니다.
  • 15분의 흔적으로 보이는 결함은 시간 초과가 아니어도 나왔습니다. 시간 안에 끝냈는데 미완성인 경우로는 cn(스크립트의 템플릿 문자열이 닫히지 않은 채 끝나 6분 9초에 SyntaxError), lfm(시작 상태에서 플레이로 넘어가는 전이가 없음), q36(시작 뒤에도 전체 화면 덮개가 CSS 명시도 때문에 남아 입력을 막음), mcv(처치한 적을 배열에서 빼지 않음)가 있습니다. 시간 초과로 잘린 것은 ff(README 없음)와 q38(경제 미검증)입니다.
  • 15분 안에 대부분 끝냈습니다. 파일을 만든 12종 가운데 10종이 9분 안에 끝났고(1분 11초 mel, 1분 33초 lfm, 1분 48초 bolt, 3분 3초 q36 …), 8분 40초 fn 이 그 가운데 가장 오래 걸렸습니다. 제한에 걸린 것은 ff·q38 뿐입니다. c1·c7r·c7 은 6~58초 만에 끝내고 파일을 만들지 못했습니다.
  • 정상 동작하는 게임을 낸 모델은 5종(ff·orn·fn·aw·mg)입니다. ff·orn 은 20웨이브 이상에 승리·재시작·배속까지 갖췄고, fn 은 업그레이드가 없고 재시작이 새로고침이며, aw 는 경제와 배치가 없고, mg 는 경로 위 배치 제한이 서술과 다르게 동작하고 재시작이 없습니다.

해석 주의

  • 표본은 모델당 1회(n=1)이고 15분이라 우연의 영향이 큽니다. mg 682 와 q38 689, aw 733 과 fn 796 처럼 가까운 구간은 순위보다 경향으로 읽어 주세요.
  • 서로 다른 장르를 같은 잣대로 줄 세운 값입니다. 1000점은 모델이 정한 규칙이 일관되게 구현됐는가를 재는 것이어서, 어느 게임이 더 재미있는지는 알려 주지 않습니다. 경제와 배치가 없는 슈팅형은 설계 항목(2절)에서 불리합니다.
  • 코드·기획 리뷰가 총점의 4할입니다. 그래서 처치한 적이 사라지지 않는 mcv 도 600점을 넘었고, 실행되지 않는 lfm 과 cn 도 실측이 0 인데 코드·기획 점수만으로 각각 207점, 182점을 받았습니다. 총점만 보고 「잘 돌아가는 게임」으로 읽지 말고 표 아래 「각 모델이 고른 게임」을 함께 봐 주세요.

시험의 한계

  • 원래 자동 시험 도구의 시작 판정에 결함이 있었습니다. 시작 버튼을 눌러도 한 번에 끝나는 변화(시작 화면이 사라짐)를 반응으로 읽지 못해 시작 실패로 판정하곤 했습니다. 시작 경로를 따로 시험하고 시작 뒤에도 화면을 덮는 층이 남는지 검사하는 개선 도구를 추가해 보완했고, 점수는 QA 의 직접 실측으로 매겼습니다. 개선 도구의 「덮는 층」 판정도 틀릴 수 있습니다. 예를 들어 bolt 에서 시작 뒤 다시 나타난 층은 CSS 명시도 문제가 아니라 1.7초 만에 뜬 승리 오버레이였습니다.
  • 실측은 헤드리스 Chrome 을 DevTools 프로토콜로 조작해 했습니다. 1280×960, 낮은 우선순위(nice 19), 한 번에 하나씩이고 모바일은 시험하지 않았습니다.
  • 후반 웨이브·승리·게임 오버처럼 오래 걸리는 상태 일부는 콘솔로 주입해 시간을 줄였습니다. 주입한 방법은 근거에 적었고, 자연 플레이로 도달할 수 있는 상태에는 70% 상한을 두지 않았습니다. 정상 플레이로 도달할 수 없어 주입으로만 본 상태(q38·lfm·q36)는 70% 상한이 걸렸습니다.
  • 시작 화면이 없는 설계(자동 시작)는 시작 입력 항목에서 감점하지 않았습니다.
  • 4-2(범위 조절의 흔적)는 실행 기록 없이 코드와 문서의 상태로만 판정했습니다. 파일 시각이 정규화돼 있어 작업 순서를 알 수 없기 때문입니다.
  • 3-3 은 PM 1인이 스크린샷으로 채점했습니다. 그래픽, 재미, 조작감, 효과음은 점수에 반영되지 않은 부분이 있습니다.
  • 네트워크 사용 관찰의 한계: 로그에 남지 않는 호출은 알 수 없고, 서브에이전트의 호출은 실행 직후 보관한 도구 호출 기록에서만 보입니다. 모델이 코드 안에서 직접 한 네트워크 접근은 그 코드가 기록에 남은 경우에만 보이므로 완전한 목록은 아닙니다.
