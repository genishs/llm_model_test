01. 브라우저 테트리스 대회

1. 한 줄 요약

같은 지시문으로 로컬 LLM 15종이 각자 브라우저용 테트리스를 만들고, 자동 실행 시험과 블라인드 코드 리뷰로 1000점 만점 채점한 대회입니다.

  • 참가 모델 15종의 제원은 00_model_info 에 있습니다.
  • 모든 모델은 같은 서버에서, 같은 에이전트 도구로, 같은 지시문을 받고, 한 번에 하나씩 순서대로 일합니다.

2. 라운드 개념 (v1 / v2 / v3)

대회는 「라운드」로 이어집니다. 같은 모델이 같은 게임을 라운드마다 한 단계씩 발전시킵니다.

라운드과제시작 상태
v1테트리스를 처음부터 새로 만들기 — 아타리(Atari Games) 1988년 아케이드판의 게임성과 그래픽 재현, index.html 하나로 실행, README.md 포함빈 폴더
v2만들어 둔 게임에 모바일 터치 조작 추가자기 v1 결과물을 복사한 폴더
v3만들어 둔 게임에 아케이드식 레벨·크레딧·컨티뉴 도입 — 지운 줄 수로 레벨이 오르고, 코인을 넣어 크레딧을 쌓아야 시작하고, 게임 오버 뒤 카운트다운 컨티뉴자기 v2 결과물을 복사한 폴더

v2·v3 의 규칙은 다음과 같습니다.

  • 각 모델은 자기 직전 라운드 결과물만(v2 는 v1, v3 는 v2) 이어받습니다. 다른 모델의 결과물은 보지 못합니다.
  • 공평성을 위해 이전 라운드 채점에서 나온 결함·피드백은 모델에게 알려 주지 않습니다. 모델은 이전 라운드에서 무엇이 틀렸는지 모른 채 지시문만 받습니다.
  • 모델마다 매번 새 세션을 시작하므로, 모델이 아는 것은 지시문과 폴더 안의 코드뿐입니다(이전 대화 기억 없음).

폴더 이름 규칙은 simple_llm_test_{모델약어}_{테스트}_{버전} 입니다.

simple_llm_test_q36_tetris_v1    # q36 모델의 v1 결과물
simple_llm_test_q36_tetris_v2    # 위 폴더를 복사해서 터치 조작을 추가한 v2 결과물
simple_llm_test_q36_tetris_v3    # v2 폴더를 복사해서 레벨·크레딧·컨티뉴를 도입한 v3 결과물

v3 도 같은 방식으로, 직전 라운드 결과물을 복사한 폴더에서 이어 갑니다.

완성되면 바꾼 파일 목록과 터치 조작 방법을 짧게 정리해 주세요.

현재 작업 폴더 이름은 simple_llm_test_{alias}_tetris_v3 입니다. 이 폴더에는 앞서 만든 HTML 테트리스 게임(터치 조작 포함)이 있습니다. 아케이드 게임처럼 레벨과 크레딧/컨티뉴 개념을 도입해 주세요.

요구사항:
- 레벨: 지운 줄 수에 따라 레벨이 오르고, 레벨이 오를수록 낙하 속도가 빨라지며, 화면에 현재 레벨이 표시되어야 합니다.
- 크레딧: 코인을 넣어 크레딧을 쌓고(키보드와 터치 모두 가능), 크레딧이 있어야 게임을 시작할 수 있게 해 주세요. 남은 크레딧을 화면에 표시해 주세요.
- 컨티뉴: 게임 오버가 되면 카운트다운과 함께 컨티뉴 화면을 보여 주고, 그 사이 크레딧을 써서 이어서 할 수 있게 해 주세요(점수·레벨 유지). 시간 안에 이어 하지 않으면 타이틀 화면으로 돌아갑니다.
- 게임 흐름: 타이틀(대기) 화면 → 시작 → 플레이 → 게임 오버 → 컨티뉴 → 타이틀 로 끊김 없이 이어지게 해 주세요.
- 기존 기능(키보드·터치 조작)은 그대로 유지하고, 별도 설치·빌드·서버 없이 index.html 을 브라우저로 열면 바로 실행되어야 합니다.
- README.md 에 레벨 규칙, 크레딧·컨티뉴 방법, 조작법을 추가해 주세요.

완성되면 바꾼 파일 목록과 크레딧·컨티뉴 조작 방법을 짧게 정리해 주세요.

4. 실행 환경

서버

  • AMD Strix Halo 노트북 서버: CPU Ryzen AI MAX+ 392(12코어), 내장 GPU Radeon 8060S, 64GB 통합 메모리.
  • 이 중 GPU 가 쓸 수 있는 공유 메모리(GTT)는 56GiB 입니다. 모델은 이 영역에 올라갑니다.
  • 모델 추론: llama.cpp b11701 (Vulkan), router 모드. 모델은 한 번에 하나만 올라가고, 요청의 모델 이름(약어)에 따라 교체됩니다.
  • 모델마다 서버에 등록된 자기 프리셋(생각 모드, 샘플링 등)을 그대로 씁니다. 대회용으로 따로 바꾸지 않았고, 각 값은 모델 정보 에 있습니다.
  • 모델 컨텍스트 길이는 대부분 65,536 토큰(Qwen2.5 계열 3종은 32,768), 1회 출력 상한은 16,384 토큰입니다.

예외: mel (Mellum 2.1)

mel 만 llama.cpp b11539 로 돌렸습니다. b11701 에는 PR #30584 가 들어 있어 Mellum 의 ffn_moe_down 연산을 F32 정밀도로 강제하는데, Vulkan 이 이 연산을 GPU 에서 지원하지 않아 CPU 로 넘어가고 생성 속도가 4.7배 느려집니다(81.7 에서 17.5 t/s). 이 서버의 GPU 에서는 b11539 에서도 NaN 이 없었고 퍼플렉서티도 같아(6.097 대 6.105) 정확도 이득 없이 속도만 잃기 때문에, mel 차례에만 엔진을 바꾸고 끝나면 b11701 로 되돌렸습니다.

에이전트

  • opencode v1.18.35 를 opencode run --auto -m halo/<약어> 로 실행합니다(--auto 는 파일 편집·명령 실행을 사람 확인 없이 허용).
  • 권한: 파일 편집 허용, 셸 명령 허용, 웹 가져오기(webfetch) 거부.
  • 모델마다 새 세션, 새 임시 홈 디렉터리에서 시작합니다.

5. 공정성 장치

장치내용
샌드박스(bubblewrap)디스크 전체를 읽기 전용으로 두고, 홈과 데이터 디스크는 빈 영역으로 가려서 다른 모델의 폴더·결과물이 보이지 않습니다. 쓸 수 있는 곳은 자기 프로젝트 폴더와 일회용 임시 홈뿐입니다. 부모 프로세스가 끝나면 함께 종료됩니다.
웹 접근 차단웹 가져오기 도구를 거부해, 인터넷에서 코드를 가져올 수 없습니다.
시간 제한모델당 최대 60분. 넘으면 강제 종료하고 그 시점의 결과물로 채점합니다.
냉각 시간모델 사이에 1분 쉽니다. 과열을 막고 직전 모델의 부하가 다음 모델에 영향을 주지 않게 하기 위해서입니다.
같은 지시문폴더 이름 외에는 동일한 지시문.
같은 순서모든 라운드에서 아래 순서를 그대로 유지합니다.
폴더 사전 생성모델이 일을 시작하기 전에 빈 폴더(v2 는 v1 복사본, v3 는 v2 복사본)를 미리 만들어 둡니다. 폴더가 이미 있으면 덮어쓰지 않고 중단합니다.

진행 순서: q36, cn, orn, mg, bolt, lfm, mcv, q38, aw, fn, ff, c7, c7r, c1, mel (mel 은 엔진을 바꿔야 해서 맨 마지막).

6. 진행 순서 (파이프라인)

모델 한 개당 다음 단계를 거치고, 15종 모두 같은 절차를 반복합니다.

 [폴더 준비]  v1: 빈 폴더 생성 / v2: 자기 v1 폴더를 복사 / v3: 자기 v2 폴더를 복사
      |
      v
 [샌드박스 에이전트 실행]  opencode + 지시문 (최대 60분)
      |
      v
 [서버 로그 집계]  소요 시간, 요청 수, 입력/생성 토큰, 생성 속도,
      |            최대 컨텍스트 길이, 컨텍스트 잘림 여부
      v
 [데스크톱 브라우저 시험]  헤드리스 Chrome (v1, v2, v3 공통)
      |
      v
 [모바일 시험]  390x844 터치 에뮬레이션 (v2, v3)
      |
      v
 [흐름 시험]  코인·크레딧·컨티뉴 아케이드 흐름 (v3 만)
      |
      v
 [냉각 1분]  --> 다음 모델

서버 로그 집계: 에이전트가 끝나면 그 시간 동안의 서버 로그에서 해당 모델 몫만 뽑아 요청 수, 읽은 토큰(프롬프트), 생성한 토큰, 생성 속도(t/s), 최대 컨텍스트 길이, 컨텍스트 초과로 잘린 횟수를 계산하고 결과 폴더의 파일 목록과 크기도 기록합니다.

데스크톱 브라우저 시험 (헤드리스 Chrome, file:// 로 index.html 을 직접 열기)

  1. 페이지 로드, 콘솔 오류·예외 수집.
  2. 시작 시도: 화면 가운데 클릭, Enter, Space 입력.
  3. 2초 동안 가만히 두고 화면이 저절로 변하는지(블록이 떨어지는지) 확인.
  4. 이동·회전·내리기 키 입력(좌, 우, 위, 아래).
  5. 스페이스(하드 드롭).
  6. 일시정지(P) 후 화면이 멈추는지 확인, 다시 P 로 재개.
  7. 약 25초 동안 키를 번갈아 눌러 연속 플레이(줄 삭제·게임 오버까지 가는지).
  8. 각 단계마다 스크린샷을 저장하고, 화면 해시 비교로 반응 여부를 판단.

모바일 시험 (v2, v3, 화면 390x844 · 터치 에뮬레이션)

  1. 휴대폰 크기로 로드하고 화면 맞춤(가로 스크롤 없음, 게임판이 화면에 들어오는지) 확인.
  2. 소스 코드에서 터치 관련 코드(touchstart 등) 검색.
  3. 화면 위 버튼 후보를 찾아 하나씩 탭하고 화면이 바뀌는지 확인.
  4. 화면 중앙 탭으로 시작, 별도의 시작 버튼이 있으면 탭.

  • 도달하기 어려운 상태는 주입으로 확인했습니다. 줄 삭제·레벨업·게임 오버는 상태를 직접 놓고 게임 자체의 코드가 돌게 했으므로, 실제 플레이에서의 도달 가능성은 별개입니다(그래서 R2 상한을 두었습니다). 코드로만 확인한 항목은 배점의 70% 이하입니다.
  • 시험의 한계. 흐름 자동 시험은 코인 키를 소스에서 추정하는 휴리스틱이고, 카운트다운·이어 하기 판정은 별도로 검증 중입니다. 그래서 이번 심사는 자동 시험의 결과가 아니라 QA 의 직접 실측으로 했습니다. 심사는 02 드래곤플라이트 생성과 같은 시간대에 돌았기 때문에, 서버 부하를 줄이려고 헤드리스 Chrome 을 낮은 우선순위(nice 19)로 한 번에 하나씩만 실행했습니다. 터치는 Chrome 의 터치 에뮬레이션이며 실제 폰이 아닙니다.
  • 일부 항목은 주관이 섞여 있습니다. 6·7절은 코드 리뷰어 1인의 판단이며, 모든 점수의 근거는 줄 번호·시험 단계·주입한 상태로 기록했습니다.
