# 01. 브라우저 테트리스 대회

## 1. 한 줄 요약

같은 지시문으로 로컬 LLM 15종이 각자 브라우저용 테트리스를 만들고, 자동 실행 시험과 블라인드 코드 리뷰로 1000점 만점 채점한 대회입니다.

- 참가 모델 15종의 제원은 [00_model_info](../00_model_info/README.md) 에 있습니다.
- 모든 모델은 같은 서버에서, 같은 에이전트 도구로, 같은 지시문을 받고, 한 번에 하나씩 순서대로 일합니다.

## 2. 라운드 개념 (v1 / v2)

대회는 「라운드」로 이어집니다. 같은 모델이 같은 게임을 라운드마다 한 단계씩 발전시킵니다.

| 라운드 | 과제 | 시작 상태 |
|---|---|---|
| **v1** | 테트리스를 **처음부터 새로 만들기** — 아타리(Atari Games) 1988년 아케이드판의 게임성과 그래픽 재현, `index.html` 하나로 실행, `README.md` 포함 | 빈 폴더 |
| **v2** | 만들어 둔 게임에 **모바일 터치 조작 추가** | **자기 v1 결과물을 복사한 폴더** |

v2 의 규칙은 다음과 같습니다.

- 각 모델은 **자기 v1 결과물만** 이어받습니다. 다른 모델의 결과물은 보지 못합니다.
- **공평성을 위해 v1 채점에서 나온 결함·피드백은 모델에게 알려 주지 않습니다.** 모델은 v1 에서 무엇이 틀렸는지 모른 채 지시문만 받습니다.
- 모델마다 매번 **새 세션**을 시작하므로, 모델이 아는 것은 지시문과 **폴더 안의 코드뿐**입니다(이전 대화 기억 없음).

폴더 이름 규칙은 `simple_llm_test_{모델약어}_{테스트}_{버전}` 입니다.

```
simple_llm_test_q36_tetris_v1    # q36 모델의 v1 결과물
simple_llm_test_q36_tetris_v2    # 위 폴더를 복사해서 터치 조작을 추가한 v2 결과물
```

이후 라운드(v3 …)도 같은 방식으로, 직전 라운드 결과물을 복사한 폴더에서 이어 갑니다.

## 3. 지시문 원문

모델마다 지시문은 폴더 이름(`__MODEL__` 자리에 모델 약어)만 다르고 나머지는 글자 하나까지 같습니다.

### v1

```text
현재 작업 폴더 이름은 simple_llm_test___MODEL___tetris_v1 입니다. 이 폴더 안에 웹 브라우저에서 바로 실행되는 HTML 기반 테트리스 게임을 만들어 주세요.

요구사항:
- 아타리(Atari Games, 1988년 아케이드판) 테트리스의 게임성과 그래픽을 최대한 가깝게 재현해 주세요.
- 별도 설치·빌드·서버 없이 index.html 파일을 브라우저로 열면 바로 실행되어야 합니다.
- 필요한 파일은 모두 이 폴더 안에 만들어 주세요.
- 게임 소개, 실행 방법, 조작법, 파일 구성을 정리한 README.md 도 이 폴더에 만들어 주세요.

완성되면 만든 파일 목록과 조작 방법을 짧게 정리해 주세요.
```

### v2

```text
현재 작업 폴더 이름은 simple_llm_test___MODEL___tetris_v2 입니다. 이 폴더에는 앞서 만든 HTML 테트리스 게임이 있습니다. 모바일 기기에서도 플레이할 수 있도록 터치 조작 기능을 추가해 주세요.
요구사항:
- 기존 기능은 그대로 유지해 주세요.
- 휴대폰 화면에서도 보기 좋게 맞춰 주세요.
- 별도 설치·빌드·서버 없이 index.html 파일을 브라우저로 열면 바로 실행되어야 합니다.
- README.md 에 터치 조작 방법을 추가해 주세요.
완성되면 바꾼 파일 목록과 터치 조작 방법을 짧게 정리해 주세요.
```

## 4. 실행 환경

**서버**

- AMD Strix Halo 노트북 서버: CPU Ryzen AI MAX+ 392(12코어), 내장 GPU Radeon 8060S, 64GB 통합 메모리.
- 이 중 GPU 가 쓸 수 있는 공유 메모리(GTT)는 56GiB 입니다. 모델은 이 영역에 올라갑니다.
- 모델 추론: llama.cpp **b11701** (Vulkan), router 모드. 모델은 **한 번에 하나만** 올라가고, 요청의 모델 이름(약어)에 따라 교체됩니다.
- 모델마다 서버에 등록된 자기 프리셋(생각 모드, 샘플링 등)을 그대로 씁니다. 대회용으로 따로 바꾸지 않았고, 각 값은 [모델 정보](../00_model_info/README.md) 에 있습니다.
- 모델 컨텍스트 길이는 대부분 65,536 토큰(Qwen2.5 계열 3종은 32,768), 1회 출력 상한은 16,384 토큰입니다.

**예외: `mel` (Mellum 2.1)**

`mel` 만 llama.cpp **b11539** 로 돌렸습니다. b11701 에는 PR #30584 가 들어 있어 Mellum 의 `ffn_moe_down` 연산을 F32 정밀도로 강제하는데, Vulkan 이 이 연산을 GPU 에서 지원하지 않아 CPU 로 넘어가고 생성 속도가 4.7배 느려집니다(81.7 에서 17.5 t/s). 이 서버의 GPU 에서는 b11539 에서도 NaN 이 없었고 퍼플렉서티도 같아(6.097 대 6.105) 정확도 이득 없이 속도만 잃기 때문에, `mel` 차례에만 엔진을 바꾸고 끝나면 b11701 로 되돌렸습니다.

**에이전트**

- opencode v1.18.35 를 `opencode run --auto -m halo/<약어>` 로 실행합니다(`--auto` 는 파일 편집·명령 실행을 사람 확인 없이 허용).
- 권한: 파일 편집 허용, 셸 명령 허용, 웹 가져오기(webfetch) **거부**.
- 모델마다 새 세션, 새 임시 홈 디렉터리에서 시작합니다.

## 5. 공정성 장치

| 장치 | 내용 |
|---|---|
| 샌드박스(bubblewrap) | 디스크 전체를 읽기 전용으로 두고, 홈과 데이터 디스크는 빈 영역으로 가려서 **다른 모델의 폴더·결과물이 보이지 않습니다**. 쓸 수 있는 곳은 **자기 프로젝트 폴더**와 일회용 임시 홈뿐입니다. 부모 프로세스가 끝나면 함께 종료됩니다. |
| 웹 접근 차단 | 웹 가져오기 도구를 거부해, 인터넷에서 코드를 가져올 수 없습니다. |
| 시간 제한 | 모델당 최대 **60분**. 넘으면 강제 종료하고 그 시점의 결과물로 채점합니다. |
| 냉각 시간 | 모델 사이에 **1분** 쉽니다. 과열을 막고 직전 모델의 부하가 다음 모델에 영향을 주지 않게 하기 위해서입니다. |
| 같은 지시문 | 폴더 이름 외에는 동일한 지시문. |
| 같은 순서 | 모든 라운드에서 아래 순서를 그대로 유지합니다. |
| 폴더 사전 생성 | 모델이 일을 시작하기 전에 빈 폴더(v2 는 v1 복사본)를 미리 만들어 둡니다. 폴더가 이미 있으면 덮어쓰지 않고 중단합니다. |

**진행 순서**: q36, cn, orn, mg, bolt, lfm, mcv, q38, aw, fn, ff, c7, c7r, c1, mel (mel 은 엔진을 바꿔야 해서 맨 마지막).

## 6. 진행 순서 (파이프라인)

모델 한 개당 다음 단계를 거치고, 15종 모두 같은 절차를 반복합니다.

```
 [폴더 준비]  v1: 빈 폴더 생성 / v2: 자기 v1 폴더를 복사
      |
      v
 [샌드박스 에이전트 실행]  opencode + 지시문 (최대 60분)
      |
      v
 [서버 로그 집계]  소요 시간, 요청 수, 입력/생성 토큰, 생성 속도,
      |            최대 컨텍스트 길이, 컨텍스트 잘림 여부
      v
 [데스크톱 브라우저 시험]  헤드리스 Chrome (v1, v2 공통)
      |
      v
 [모바일 시험]  390x844 터치 에뮬레이션 (v2 만)
      |
      v
 [냉각 1분]  --> 다음 모델
```

**서버 로그 집계**: 에이전트가 끝나면 그 시간 동안의 서버 로그에서 해당 모델 몫만 뽑아 요청 수, 읽은 토큰(프롬프트), 생성한 토큰, 생성 속도(t/s), 최대 컨텍스트 길이, 컨텍스트 초과로 잘린 횟수를 계산하고 결과 폴더의 파일 목록과 크기도 기록합니다.

**데스크톱 브라우저 시험 (헤드리스 Chrome, `file://` 로 index.html 을 직접 열기)**

1. 페이지 로드, 콘솔 오류·예외 수집.
2. 시작 시도: 화면 가운데 클릭, Enter, Space 입력.
3. 2초 동안 가만히 두고 화면이 저절로 변하는지(블록이 떨어지는지) 확인.
4. 이동·회전·내리기 키 입력(좌, 우, 위, 아래).
5. 스페이스(하드 드롭).
6. 일시정지(P) 후 화면이 멈추는지 확인, 다시 P 로 재개.
7. 약 25초 동안 키를 번갈아 눌러 연속 플레이(줄 삭제·게임 오버까지 가는지).
8. 각 단계마다 스크린샷을 저장하고, 화면 해시 비교로 반응 여부를 판단.

**모바일 시험 (v2, 화면 390x844 · 터치 에뮬레이션)**

1. 휴대폰 크기로 로드하고 **화면 맞춤**(가로 스크롤 없음, 게임판이 화면에 들어오는지) 확인.
2. **소스 코드에서 터치 관련 코드**(touchstart 등) 검색.
3. 화면 위 **버튼 후보를 찾아** 하나씩 탭하고 화면이 바뀌는지 확인.
4. 화면 중앙 탭으로 시작, 별도의 시작 버튼이 있으면 탭.
5. **스와이프**(좌우, 아래 등)와 **탭** 제스처 시험.
6. **일시정지** 버튼을 따로 시험.
7. 약 20초 동안 터치를 섞어서 연속 플레이.

### 채점 방법

- **블라인드 리뷰**: 결과물에 익명 이름(A~O)을 붙여 채점하고, 채점이 끝난 뒤 모델 이름을 공개합니다. 리뷰어는 어느 모델이 만든 것인지 모른 채 채점합니다.
- **영역별 담당이 다릅니다.**
  - **1-1 실행·안정성, 1-2 핵심 규칙**: QA 리뷰어 한 명이 헤드리스 브라우저로 직접 실행해 검증한 결과로 채점합니다(코드 리뷰어의 1-2 점수는 코드 판독만으로 낸 교차 확인용 추정치라 총점에 넣지 않습니다).
  - **2~6 (코드 간결성, 모듈 분리, 의존성, 파일 배분, README)**: QA 리뷰어와 코드 리뷰어가 각자 매긴 점수의 **평균**입니다.
  - **1-3 아타리 재현**: 진행자(PM)가 실행 스크린샷을 보고 채점합니다.
- **아타리 재현 부분**은 원작 세부 규칙을 확신하지 못하면 감점 근거로 쓰지 않고, 「원작에 맞추려는 의도와 일관성」을 봅니다.
- **모든 감점·가점에는 근거**(파일:줄 번호 또는 시험 결과)를 적어야 합니다. 근거 없는 감점은 금지입니다.
- 아무것도 만들지 못했거나 실행이 안 되면 1-1 은 0점이고, 나머지는 있는 코드만큼만 채점합니다.
- **채점 정정(투명성 기록)**: 1-3 을 처음 채점할 때 진행자가 `cn`·`q38` 도 다른 모델처럼 하드드롭을 쓴 것으로 잘못 보았습니다. 두 모델은 하드드롭 없이 아래 키로 빨리 내리기만 쓰는데, 이를 원작의 조작 방식에 맞다고 보고 1-3 조작감을 올려 `cn` 55점에서 65점, `q38` 63점에서 73점으로 정정했습니다. 두 모델의 총점은 각각 10점 올랐고(`cn` 729.5, `q38` 742.5) 순위는 바뀌지 않았습니다.

### 실용 순위

1000점 순위와 별도로, **600점 이상**인 결과물만 모아 **만드는 데 걸린 시간 순**으로 나열한 「실용 순위」를 함께 냅니다.

속도는 1000점에 넣지 않았습니다. 같은 서버라도 모델 크기·엔진 설정에 따라 속도가 크게 갈려서, 속도를 점수에 섞으면 품질 비교가 흐려지기 때문입니다. 대신 쓸 만한 품질(600점 이상)을 갖춘 모델 사이에서 얼마나 빨리 끝냈는지를 별도 순위로 보여 줍니다.

### 눈에 띈 점

- **`ff` 가 1위(924점)이고, 시작·이동·회전·드롭·일시정지·재개를 터치만으로 한 화면에서 모두 해낸 유일한 모델입니다.** 터치 286/300, 화면 맞춤 144/150 으로 둘 다 1위입니다. 하단에 「회전 2개 + DROP / 좌우 + ▼ + II / START」 세 묶음 버튼을 두고 보드 위 스와이프·탭도 받습니다. 시험에서 모든 버튼이 한 번에 맞게 동작했고 보드·점수·NEXT·버튼이 844px 높이 안에 들어왔습니다(세로 14px 초과). 감점은 길게 눌러도 반복되지 않는 점(1초를 눌러 한 칸), 힌트 문구가 오른쪽에서 잘리는 점 정도입니다. 코드도 1위(4절 173/200)입니다. 버튼을 `data-act` 속성과 `doAction` 디스패처 하나로 묶었습니다(다만 키보드는 이 디스패처를 거치지 않는 별도 switch). 5분 27초, 요청 16회에 끝냈습니다.
- **2~5위(`aw`·`q38`·`mg`·`q36`)는 터치 버튼이 입력은 받았지만 각자 하나씩 빠졌습니다.** `aw`(816)는 변경이 순수 추가형(+158/−0)이고 길게 누르기 반복도 되는데, v1 의 자동 낙하 없음이 그대로라 ↓ 를 눌러야만 내려오고, 터치 일시정지가 없으며 버튼 폭이 33px 로 좁습니다. `q38`(782)은 4버튼(◀▶⟳▼, ▼ 길게 누르면 연속)이 입력을 받고 safe-area 까지 챙겼지만, v1 의 충돌 결함(이중 오프셋)이 그대로라 조각이 맨 아래 행(19행)이 아니라 10행에서 굳고, 오른쪽으로는 열 6 까지만(끝 열은 9) 가며, 줄을 지울 수 없습니다. 일시정지 기능도 애초에 없고, README 의 「화면 아무 곳이나 탭하면 시작」은 사실이 아닙니다(버튼을 눌러야 시작). `mg`(736)는 버튼과 스와이프를 모두 넣고 README 도 정확하지만(v1 8위에서 4위로) START 버튼이 하단 고정 바에 가려져 윗 9px 띠만 눌리고, 하드드롭(■)은 v1 의 예외를 그대로 복제해 게임을 죽이며, 일시정지 뒤 재개를 누르면 새 게임이 시작됩니다. `q36`(696)은 큰 버튼 6개가 동작하지만 터치로 게임을 시작할 방법이 없고(Enter/Space 뿐), 새로 만든 HOLD 버튼이 v1 의 버그(첫 홀드 = 게임오버)를 그대로 드러냅니다.
- **터치가 아무것도 못 한 모델이 6종(`lfm`·`mel`·`bolt`·`orn`·`mcv`·`fn`)이고, 원인은 제각각이지만 모두 한 번만 눌러 봐도 드러납니다.** 이들의 터치 점수는 모두 0/300 입니다.
  - `lfm`: 터치 리스너를 `canvas` 에 달았는데 이 이름은 정의돼 있지 않습니다(변수는 `CANVAS`, index.html 306줄). ReferenceError 로 스크립트가 거기서 멈춰 `startGame()` 도 실행되지 않습니다. v1 도 이미 빈 보드였습니다.
  - `mel`: 붙여넣다 남은 `startGame(); });` 두 줄 때문에 `script.js` 가 문법 오류가 되어 통째로 실행되지 않습니다. 터치 버튼도 CSS 에 `display:none` 만 있어 늘 숨겨져 있습니다. v1 에서 키 입력에 반응하던 게임이 키보드까지 죽었으므로 **이번 회차의 유일한 명백한 회귀**이고, 순위가 9위에서 12위(498 → 175)로 내려갔습니다.
  - `bolt`: 터치 판정에 `getBoundingClientRect().contains(x, y)` 를 썼는데 `DOMRect` 에는 `contains` 메서드가 없어 터치마다 TypeError 가 납니다(618줄). v1 의 시작 단계 예외(`window.nextPiece`)도 그대로입니다.
  - `orn`: 로드할 때 `drawNext()` 가 `nextQueue[0]` 에서 TypeError(v1 부터 있던 초기 렌더 예외)를 내고, 그 뒤의 `fit()`·터치 UI 만들기·낙하 루프가 실행되지 않습니다. 코드 리뷰어는 입력 구조(버튼과 제스처가 한 액션 맵을 공유, 액션이 상태 가드를 내장)를 12종 중 최고로 보았지만 실행되지 않았습니다.
  - `mcv`: viewport 메타가 없어 폰이 980px 폭 레이아웃으로 그리고, 터치 버튼이 들어 있는 `@media (max-width:600px)` 가 걸리지 않아 버튼이 계속 숨겨집니다. 터치로 시작할 방법도 없습니다(시작은 Enter 뿐). README 는 「터치 컨트롤 자동 표시」라고 적었습니다. **지난 라운드 1위(786.5)가 7위(447)로 떨어졌습니다.**
  - `fn`: 아래 항목 참고.
- **`fn` 은 v2 에서 처음으로 게임을 만들었지만 돌아가지 않습니다.** v1 폴더가 비어 있어 지시문의 「앞서 만든 게임」이 없었는데도 처음부터 만들었고(448초, 요청 17회, 생성 7,804토큰으로 이번 회차에서 가장 오래 걸림) 그래서 v1 의 0점에서 365점이 됐습니다. 다만 `reset()` 이 첫 조각을 만들지 않아 첫 입력과 중력부터 `cur` 접근 예외가 나고 보드가 계속 비어 있으며, RESTART 버튼이 늘 보여 ▶·▼ 버튼 위를 가립니다. 반면 `c7`·`c7r`·`c1` 은 v2 에서도 파일을 하나도 만들지 못했습니다(생성 토큰 1,134·52·125개, 8~62초에 종료. 원인은 분석하지 않았습니다).
- **어떤 모델도 v1 의 버그를 고치지 않았습니다(QA 가 diff 전수 확인).** 바로 옆 코드를 만지고도 그랬습니다. `mg` 는 keydown 블록을 들여쓰기까지 손대고도 하드드롭의 `pos.y++` 오류를 그대로 두었고 새 `hardDrop()` 에 복제했습니다. `orn` 은 `fit()` 을 고치면서 바로 아래 init 의 예외는 두었습니다. `aw` 는 중력의 시간 비교 오류(208줄의 `Date.now()` 와 470줄 `requestAnimationFrame` 타임스탬프를 비교)를 안 고쳐서, 버튼을 아무리 잘 달아도 조각이 저절로 내려오지 않습니다. `q38` 의 충돌 이중 오프셋도 v1 코드 그대로입니다. `mcv` 의 일시정지 뒤 재개 불능, `q36` 의 HOLD = 게임오버, `bolt` 의 시작 예외도 모두 그대로이고, 1위 `ff` 도 게임 로직은 건드리지 않았습니다(+158/−5). 터치 버튼이 오히려 이 버그들을 더 쉽게 드러냈습니다(`mg` 의 ■, `q36` 의 HOLD). 다만 모델은 v1 의 피드백을 받지 못한 채 작업했으므로 이를 감점하지 않고 「v1 대비 개선」 50점을 중립 25점 기준으로 두었습니다.
- **README 가 실제 동작과 어긋난 곳이 많습니다.** 파일이 있는 12종 중 8종에서 코드와 다른 주장이 나왔습니다(`ff` 도 「보드 제스처가 클릭도 지원」 한 줄은 틀립니다). `cn`: 「캔버스 탭 = 회전」(실제로는 무반응. `touchstart` 의 `preventDefault` 가 click 합성을 막고, `handleTouchTap` 은 등록되지도 않음). `q38`: 「화면 아무 곳이나 탭하면 시작」(버튼만 시작). `mcv`: 「overlay 의 시작 버튼」「터치 컨트롤 자동 표시」(없거나 숨겨짐). `lfm`: 「화면 상단의 일시정지 버튼」(없음). `orn`: 「하드 드롭: 화면을 두 번 탭」(실제로는 한 번 탭). `mel`: 한 줄 README 가 적은 drop 버튼(없음). `fn`: RESTART 는 「게임 오버 때 나타남」(늘 보임). `q36`: 터치로 시작·일시정지할 방법이 없다는 사실은 적지 않고 index.html 만 열면 바로 플레이할 수 있다고만 적었습니다. 코드 리뷰어가 「거의 정확」하다고 본 것은 `ff`(46)·`aw`(46)·`mg`(45) 3종이고 5절 점수는 10~46/50 입니다.
- **화면에 맞추는 일에서 함정이 반복됐습니다.** 버튼이 한 화면 밖에 있는 경우(`cn` 은 조작 패널이 화면 아래로 밀려 전체 높이가 1.5화면, `bolt` 는 버튼 격자가 아래에 있고 body 를 flex 로 가운데 정렬해 캔버스 윗부분이 화면 위로 밀려나 스크롤로도 닿지 않음)와, 고정 오버레이가 자기 버튼을 가리는 경우(`mg` 의 START, `fn` 의 RESTART 가 ▶▼ 를 가로챔)가 있었습니다. `aw` 는 버튼 폭이 33px 로 엄지 기준 44px 에 못 미쳤습니다. `q38` 은 66×66 버튼에 safe-area 도 반영했지만 가로 맞춤 축소로 보드 폭이 약 153px 로 작습니다.

### 해석 주의

- **표본은 모델당 1회(n=1)입니다.** 점수 차이가 작은 구간(예: `q36` 696 과 `cn` 678, `mcv` 447 과 `orn` 446)은 순위보다 경향으로 읽어 주세요.
- **v2 총점의 700점(1·2·3)이 실행 검증이라, 실제로 터치가 되느냐가 순위를 거의 정합니다.** 코드 점수(4·5·6)는 300점뿐이어서 코드 구조가 좋아도(`orn`) 실행이 안 되면 1절 300점을 통째로 잃고, 실제로 터치가 안 된 6종은 175~447점에 머물렀습니다. 원작 재현(v1 의 1-3)은 이번 라운드에서 평가하지 않았습니다.
- **3절 「기존 기능 유지」는 「v1 과 달라졌나」를 보는 항목이라, 처음부터 죽어 있던 게임도 「그대로 죽어 있음」으로 일부 점수를 받습니다.** `orn` 150, `bolt` 145 가 그 예입니다(v1 과 같은 동작이라는 비교 점수 100점이 들어 있음). `fn` 은 v1 이 비어 있어 비교 기준이 없어 중립으로 처리했고(3절 90/250), 4절은 변경분 대신 새 코드 자체를 평가했습니다.
- **QA 재검증 기록.** `q38` 의 충돌 결함(바닥 10행에서 굳음·우측 열 6 까지만·줄 삭제 불가)을 재검증으로 확인해 1·3절을 감점했고, 3-1(b) 는 항목 공식으로 전 엔트리에 다시 적용함(원점수는 QA 문서에 보존). 그 결과 `q38`(782)은 `aw`(816) 아래로 내려갔고, 인상으로 주던 점수가 항목별 점수로 바뀌면서 `aw`·`mg`·`q36`·`cn`·`mcv` 의 3절이 3~13점 올랐습니다.
- **`mel` 의 「회귀」는 키 입력에 대한 게임 상태 변화를 기준으로 한 판단입니다.** v1 채점에서는 화면이 그려지지 않는 것으로 기록된 게임이므로, v1 도 보이는 화면으로는 온전히 플레이된 것은 아닙니다.
- **시험의 한계.** 줄 삭제는 재검증에서 바닥 행을 미리 채워 두고 조각을 떨어뜨리는 방식으로 확인했을 뿐, 여러 조각을 쌓아 완성하는 일반 경로는 직접 보지 않았습니다. 점수·레벨 곡선은 확인하지 않았습니다. 터치는 Chrome 의 터치 이벤트 에뮬레이션이며 실제 폰이 아닙니다(iOS Safari 의 더블탭 확대, 주소창 높이 변화, 길게 누르기 메뉴는 재현되지 않음). 터치로 시작할 수 없는 모델(`q36`)은 진단용으로만 키보드로 시작해 나머지 버튼을 확인하고 그만큼 감점했습니다(이동·회전·내리기 ×0.8). 4·5·6 은 코드 리뷰어가 브라우저를 띄우지 않고 diff 와 파일을 읽어 채점했습니다(스크립트 문법만 검사).
- **일부 항목은 주관이 섞여 있습니다.** 직관성, 화면 배치, diff 깔끔함, 입력 구조는 리뷰어 1인의 판단이며 근거는 줄 번호나 시험 단계로 기록했습니다.
